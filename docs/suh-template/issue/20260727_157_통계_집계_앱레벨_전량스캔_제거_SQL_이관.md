🗒️ 설명
---

`backend/src/services/stats_service.py`의 통계 집계가 DB에서 처리 가능한 계산을 앱 레벨로 끌어와서 수행한다. 플레이 횟수가 늘어날수록 응답 시간이 선형으로 나빠진다.

**1. 전체 세션 JSONB를 파이썬으로 끌어옴** (`get_player_stats`, 101행)

```python
ss_res = await db.execute(
    select(GameSession.stage_scores).where(GameSession.nickname == nickname)
)
for row in ss_res.scalars().all():   # 유저의 전체 세션을 순회
```

날짜 필터가 없어 해당 유저의 **모든** 세션 JSONB가 네트워크를 타고 넘어온다.

**2. 전체 타임스탬프를 끌어와 파이썬 루프** (139행)

```python
gap_res = await db.execute(
    select(GameSession.played_at).where(GameSession.nickname == nickname).order_by(...)
)
times = list(gap_res.scalars().all())
for i in range(1, len(times)):       # 세션 간격을 파이썬에서 계산
```

역시 날짜 필터가 없다. `LAG()` window function이면 SQL 한 방에 끝난다.

**3. 순차 await 8회 이상**

`get_player_stats` 안의 쿼리들이 서로 의존하지 않는데도 전부 순차 실행된다. round-trip이 그대로 누적된다.

**4. public-stats가 가장 비싼 계산을 하고 버림** (`stats_router.py:40`)

```python
full = await stats_service.get_player_stats(db, nickname)  # habit·hardest 전부 계산
...
public_words = {"played": ..., "most_played": ..., "easiest": ...}  # hardest 버림
```

랭킹 화면에서 다른 사람 프로필을 열 때마다, 응답에 담지도 않을 `habit`(전체 세션 스캔 2회)과 `words.hardest`를 계산한다. 랭킹은 트래픽이 가장 많은 화면이다.

**5. 전체 통계 풀스캔** (`get_global_stats`)

`game_sessions` 전체에 `percentile_cont` + 1000점 버킷 `GROUP BY`를 돌린다. 5분 인메모리 캐시가 있지만 단일 프로세스 한정이고, 캐시 만료 시점마다 풀스캔이 재발생한다.

**6. `players.best_score` 인덱스 없음**

```python
select(Player).order_by(Player.best_score.desc()).limit(limit).offset(offset)   # 랭킹
select(func.count()).where(Player.best_score < player.best_score)               # 백분위
```

두 쿼리 모두 매번 full scan + sort를 유발한다. `game_sessions`에는 복합 인덱스가 잘 잡혀 있는데 `players`에만 빠져 있다.

🔄 재현 방법
---

1. 특정 닉네임으로 게임을 수백 회 플레이해 `game_sessions` 행을 쌓는다
2. 통계 화면(`/stats`)에 진입한다
3. 응답 시간이 플레이 횟수에 비례해 증가한다
4. 랭킹 화면에서 해당 유저 행을 클릭해 공개 통계 모달을 연다 → 노출되지도 않는 habit 계산까지 수행되어 동일하게 느리다

📸 참고 자료
---

`X-Process-Time` 응답 헤더(`main.py:158`)로 각 요청의 처리 시간을 확인할 수 있다.

현재 `game_sessions`는 인덱스가 잘 잡혀 있다:

```python
Index("ix_game_sessions_nickname_played_at", "nickname", "played_at"),
Index("ix_game_sessions_played_at", "played_at"),
```

반면 `players`는 `nickname` unique 인덱스만 있고 `best_score` 인덱스가 없다.

✅ 예상 동작
---

- 개인 통계 응답 시간이 플레이 횟수에 크게 좌우되지 않아야 한다
- 공개 통계(`public-stats`)는 실제로 응답에 담는 항목만 계산해야 한다
- 랭킹 정렬과 백분위 계산이 인덱스를 타야 한다

🛠️ 해결 방안
---

1. **집계를 SQL로 이관**
   - `stage_best`: `jsonb_each_text` + `GROUP BY`로 DB에서 집계
   - `session_gap_minutes`: `LAG(played_at) OVER (ORDER BY played_at)` window function으로 계산
   - 두 쿼리 모두 최근 30일 날짜 필터를 적용한다 (`habit`의 다른 항목들과 기준 통일)
2. **public-stats 전용 경로 분리** — `get_player_stats`를 그대로 호출하지 않고, 공개 항목만 계산하는 `get_public_stats()`를 별도로 만든다. habit·hardest는 애초에 쿼리하지 않는다
3. **독립 쿼리 병렬화** — 서로 의존하지 않는 쿼리를 `asyncio.gather`로 묶는다. 단, `AsyncSession`은 동시 사용이 불가하므로 세션을 분리하거나 쿼리 자체를 하나로 합치는 방식 중 실측이 나은 쪽을 택한다
4. **인덱스 추가** — `players.best_score`에 내림차순 인덱스를 alembic 마이그레이션으로 추가한다
5. **측정** — 수정 전후로 `X-Process-Time`을 비교해 개선 폭을 보고서에 기록한다
